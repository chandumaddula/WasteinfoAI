# wasteinfoAI — Database Schema

> Related: [architecture](architecture.md) · [system workflow](system_workflow.md) · [API documentation](api_documentation.md) ·
> [`database/README.md`](../database/README.md)

Verified on 2026-10-13 against the SQLAlchemy models (`backend/app/models/`), the Alembic migration, and a live PostgreSQL 16
database created by `alembic upgrade head`.

- **Database engine:** PostgreSQL 16 (Docker image `postgres:16-alpine`), driver psycopg 3, SQLAlchemy 2.x.
- **Default local names** (from `docker-compose.yml` / `backend/.env.example`): database and user `wasteinfoai`, host port 5432 on loopback.
- **Migration head:** `a1f3c2d4e5b6` ("service layer foundation", file `backend/alembic/versions/20261011_0541_a1f3c2d4e5b6_service_layer_foundation.py`). It is the only revision and has no parent.
- **Tables (4 + Alembic's `alembic_version`):** `institutions`, `users`, `waste_reports`, `report_events`.

## 1. Entity relationships

```
 institutions 1 ───< users            (users.institution_id, nullable)
 institutions 1 ───< waste_reports    (waste_reports.institution_id, nullable; copied from the submitter at creation)
 users        1 ───< waste_reports    (owner_id [required], assigned_worker_id, reviewed_by_id)
 waste_reports 1 ──< waste_reports    (duplicate_of_id, self-reference)
 waste_reports 1 ───< report_events   (report_id)
 users        1 ───< report_events    (actor_id)
```

## 2. Conventions
- **Primary keys:** `uuid`, generated by the application (`uuid4`).
- **Timestamps:** `timestamp with time zone`, set by the application in UTC (server-generated; clients cannot set them).
- **No database-side defaults:** no column has a `DEFAULT`; defaults live in the application. Inserts outside the application must supply every NOT NULL column.
- **Enumerations** (role, status, event type) are `varchar` guarded by `CHECK` constraints, not PostgreSQL `ENUM` types.
- **Foreign keys** are all `ON DELETE NO ACTION` (rows referenced elsewhere cannot be deleted); the API has no delete operations.
- **Constraint naming:** deterministic names from the metadata naming convention (`pk_`, `fk_`, `uq_`, `ck_`, `ix_` prefixes).

## 3. `institutions`
Minimal tenant record. There is no API to manage institutions yet.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | **PK** `pk_institutions` |
| `name` | varchar(200) | no | **Unique** `uq_institutions_name` |
| `created_at` | timestamptz | no | |

## 4. `users`
Identity records used to resolve role and institution on each request. No password or credential columns exist.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | **PK** `pk_users`; equals the token `sub` |
| `email` | varchar(320) | no | **Unique** `uq_users_email` |
| `role` | varchar(32) | no | `RESIDENT`, `INSTITUTION`, `REVIEWER`, `SANITATION_WORKER`, `ADMIN` |
| `institution_id` | uuid | yes | **FK** → `institutions.id` (`fk_users_institution_id_institutions`) |
| `is_active` | boolean | no | inactive users are rejected with 401 |
| `created_at`, `updated_at` | timestamptz | no | |

Checks: `ck_users_role_valid` (role in the five values); `ck_users_email_lowercase` (`email = lower(email)`);
`ck_users_institution_role_requires_institution` (`role <> 'INSTITUTION' OR institution_id IS NOT NULL`).
Indexes: PK and unique email only.

## 5. `waste_reports`

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | **PK** `pk_waste_reports` (server-generated report id) |
| `owner_id` | uuid | no | **FK** → `users.id`; derived from the authenticated user |
| `institution_id` | uuid | yes | **FK** → `institutions.id`; copied from the owner when the report is created |
| `client_uuid` | uuid | no | client-generated idempotency key |
| `request_fingerprint` | varchar(64) | no | SHA-256 hex of the canonical create payload; fixed at creation, never updated |
| `waste_category` | varchar(64) | no | validated by the application against the category registry (not a database constraint) |
| `description` | text | no | normalized, ≤ 2000 chars enforced by the application |
| `latitude`, `longitude` | double precision | yes | plain numbers; no PostGIS / geometry type |
| `manual_location` | varchar(200) | yes | |
| `evidence_ref` | varchar(255) | yes | opaque storage key; existence never verified |
| `client_created_at` | timestamptz | yes | device time, informational only |
| `status` | varchar(16) | no | `UNDER_REVIEW`, `VERIFIED`, `ASSIGNED`, `RESOLVED`, `REJECTED`, `DUPLICATE` (workflow status; **not** a sync state) |
| `duplicate_of_id` | uuid | yes | **FK** → `waste_reports.id` (self) |
| `assigned_worker_id` | uuid | yes | **FK** → `users.id` |
| `reviewed_by_id` | uuid | yes | **FK** → `users.id` |
| `reviewed_at` | timestamptz | yes | |
| `review_note` | varchar(500) | yes | |
| `created_at`, `updated_at` | timestamptz | no | `updated_at` is the synchronization ordering key |
| `version` | integer | no | optimistic-concurrency token (SQLAlchemy `version_id_col`), starts at 1 |

**Unique:** `uq_waste_reports_owner_client_uuid` on `(owner_id, client_uuid)` — the database-level idempotency guarantee.

**Check constraints**

| Name | Rule |
|---|---|
| `ck_waste_reports_status_valid` | status is one of the six values |
| `ck_waste_reports_latitude_range` / `_longitude_range` | −90…90 / −180…180 when present |
| `ck_waste_reports_coordinates_paired` | `(latitude IS NULL) = (longitude IS NULL)` |
| `ck_waste_reports_location_present` | `latitude IS NOT NULL OR manual_location IS NOT NULL` |
| `ck_waste_reports_description_not_blank` | `length(btrim(description)) > 0` |
| `ck_waste_reports_duplicate_link` | `(status = 'DUPLICATE') = (duplicate_of_id IS NOT NULL)` |
| `ck_waste_reports_duplicate_not_self` | `duplicate_of_id IS NULL OR duplicate_of_id <> id` |
| `ck_waste_reports_assignment_required` | `status NOT IN ('ASSIGNED','RESOLVED') OR assigned_worker_id IS NOT NULL` |
| `ck_waste_reports_version_positive` | `version >= 1` |

**Indexes (besides the PK and the unique constraint)**

| Index | Columns | Serves |
|---|---|---|
| `ix_waste_reports_owner_id_created_at` | `(owner_id, created_at)` | resident/owner listings |
| `ix_waste_reports_created_at_id` | `(created_at, id)` | `GET /reports` keyset pagination |
| `ix_waste_reports_updated_at_id` | `(updated_at, id)` | `GET /sync/changes` keyset pagination |
| `ix_waste_reports_status` | `(status)` | status filter |
| `ix_waste_reports_institution_id` | `(institution_id)` | institution visibility |
| `ix_waste_reports_assigned_worker_id` | `(assigned_worker_id)` | worker visibility |

## 6. `report_events` (audit trail, append-only by convention)

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | **PK** `pk_report_events` |
| `report_id` | uuid | no | **FK** → `waste_reports.id` |
| `actor_id` | uuid | no | **FK** → `users.id` |
| `event_type` | varchar(32) | no | `CREATED`, `UPDATED`, `STATUS_CHANGED` (`ck_report_events_event_type_valid`) |
| `from_status`, `to_status` | varchar(16) | yes | set for status events (`to_status` also on `CREATED`) |
| `note` | varchar(500) | yes | review/resolve note, or `fields: a,b` for `UPDATED` |
| `report_version` | integer | no | report version after the change |
| `created_at` | timestamptz | no | |

Index: `ix_report_events_report_id_created_at` on `(report_id, created_at)`. Rows are written in the same transaction as the
change they describe. The database does not block updates or deletes of events (no trigger/permission is defined), and no
API reads them yet.

| `fk_users_institution_id_institutions` | `users.institution_id` → `institutions.id` |

| `fk_waste_reports_institution_id_institutions` | `waste_reports.institution_id` → `institutions.id` |
| `fk_waste_reports_duplicate_of_id_waste_reports` | `waste_reports.duplicate_of_id` → `waste_reports.id` |
| `fk_waste_reports_assigned_worker_id_users` | `waste_reports.assigned_worker_id` → `users.id` |
| `fk_waste_reports_reviewed_by_id_users` | `waste_reports.reviewed_by_id` → `users.id` |

Alembic additionally maintains its own `alembic_version` table (one row: the current revision id).

## 8. Schema management
- **Alembic is the only schema owner.** Models live in `backend/app/models/`; `alembic/env.py` reads the same settings as the application
  and `Base.metadata`. Tables are never created at application start-up or by hand in SQL.
- **Workflow** (run from `backend/`):
  ```powershell
  alembic upgrade head                                   # apply
  alembic current                                        # show the applied revision (expect a1f3c2d4e5b6)
  alembic revision --autogenerate -m "describe change"   # draft; always review before committing
  alembic downgrade -1                                   # roll back one revision (destructive: drops data in dropped objects)
  ```
- Add each new model module to `app/models/__init__.py` so autogenerate sees it. Never edit an applied revision; add a new one.
  Prefer additive, non-destructive migrations.
- **Tests that guard the schema** (PostgreSQL integration tests): upgrade → downgrade → upgrade round-trip, "models match migrations"
  (autogenerate diff is empty), and tests that provoke the unique and check constraints directly.
- `database/init/` holds no scripts (PostgreSQL's first-boot hook is not needed) and `database/seeds/development_rules.sql` is a read-only
  placeholder; see [`database/README.md`](../database/README.md).

## 9. Planned, not implemented
- **Disposal rules:** there is **no** disposal-rules table, model, API or content. It would require a SQLAlchemy model plus an Alembic migration,
  the canonical 17 category labels, and reviewed content first.
- **Category registry in the database:** categories live in `backend/config/waste_categories.json`, not in a table (currently empty).
- **Evidence/file metadata**, credentials/identity tables, spatial (PostGIS) columns, and any retention/deletion policy are not present.
